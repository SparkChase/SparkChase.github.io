Terraform实践：从一台腾讯云服务器到可复用的环境

发表于 2026-10-07|更新于2026-10-07|AIOps
|字数总计:4087|阅读时长:14分钟|阅读量:

前两篇《IaC和Terraform概述》和《Terraform概述》把配置、Provider 和 state 串了起来。开始操作之前，还需要弄清凭证放在哪里、创建失败后怎样继续，以及实验结束时怎么确认资源已经清理干净。

课程的 module_2 恰好提供了一条逐渐展开的路线：先创建腾讯云 CVM 和安全组，再引入远程状态，接着安装 K3s、部署 Argo CD，最后提取模块管理不同环境。

下面先整理一个可以独立操作的 CVM 实验，再分析后面的组合方式。示例基于课程代码调整，需要填入自己的云账号资源参数；这里没有提供一次真实云部署的成功记录。

先确定这次实验管理哪些资源

这次创建一台 CVM、一个安全组和对应规则，复用已有的 VPC、子网。这样第一次实验就可以集中观察资源创建、依赖和 state，清理时也不会涉及已有网络的生命周期。

准备时需要确认：

  • 已安装 Terraform，terraform version 能正常输出版本。
  • 云账号具备相关资源的查询和管理权限，并有可用额度。
  • 已有 VPC 和子网，子网所属地域、可用区与实例配置一致。
  • 已确认可用的 Ubuntu 镜像 ID、实例规格和系统盘类型。
  • 知道当前管理端的公网出口 IP，用于限制 SSH 的来源。

课件直接查询可用区、镜像和机型，并取结果列表的第一项。这种写法容易看懂，但几个独立列表的第一项未必能组成一套可用配置。这里把结果改为显式输入，先在同一可用区确认一组可购买的参数，再交给 Terraform。

实验资源会产生费用，包括实例和可能产生的网络费用。创建前检查计费方式，用完后检查销毁结果。

从本地 state 迁移到 COS

个人练习可以先用本地状态。换电脑或者交给另一个人执行时，就需要避免各自拿着不同的状态记录工作。

继续接上 K3s 和 Argo CD，会遇到什么？

demo_4 把流程拆成了 cvm.tf、k3s.tf 和 helm.tf。文件拆开之后，依赖仍然存在：

课程中的 K3s 模块引用服务器的公网和私网 IP，再通过 SSH 安装。后面使用 remote-exec 在服务器上准备 kubeconfig，使用 local-exec 将它下载到执行 Terraform 的机器。

这段代码很适合解释 provisioner 的位置：remote-exec 在远端执行，local-exec 在本地执行。换到 CI runner 后，本地路径、SSH 密钥和工具是否存在，都要重新考虑。provisioner 通常伴随资源创建等生命周期事件执行，远端文件丢失也不会自动触发一次通用修复。

如果沿这条路线继续做，需要允许管理端访问 K3s API，并检查服务就绪和 kubeconfig。课程的具体 K3s 版本与模块来源属于当时的示例，复现前应核对兼容性和模块版本。

为什么加了 depends_on，Helm 仍可能失败？

课程的 Helm Provider 读取本地 config.yaml，这个文件却是在同一轮执行中稍后下载的。即使给 helm_release 加上资源依赖，Provider 在规划、刷新或初始化相关操作时，也可能已经需要读取文件或连接集群。

dev 和 testing 怎样复用？

复制整个目录能快速得到第二套环境，但公共逻辑改动后就要修改多份代码。课件 demo_5 用模块解决这部分重复：

这里有两个值得检查的细节。课件中根模块声明了 region，但调用 CVM 模块时没有传下去；K3s 模块也有密码输入，调用处却依赖默认值。只修改根模块的地域或密码后，模块内部未必会跟着改变。

所以检查模块化代码时，我会沿着“根变量、模块参数、模块内部引用”逐段核对。把文件搬进 modules 目录，并不能保证输入已经正确接通。

上面省略了课程中的凭证参数，按前面的方式交给 Provider 从环境变量读取。整理成通用模块时，还可以在根模块配置 Provider，子模块声明所需 Provider 并继承调用者的配置，减少账号和地域配置散落在内部的问题。

dev 和 testing 各自配置输入和 backend 路径，不能只换一个实例名称却共用同一份状态。模块代码更新后，也需要分别进入各环境查看计划、决定何时应用；模块复用不会自动更新已经运行的环境。

如果已有资源从根模块迁入子模块，还要处理资源地址变化。应使用 moved 块或合适的状态迁移方式保持映射，先确认 plan 不会把“整理代码”解释成“删旧建新”。

实验结束，确认资源真的被清理

对于前面独立的 CVM 实验，可以先生成销毁计划：

检查计划只包含这个目录管理的实验资源。已有 VPC、子网是输入参数，不在销毁范围内；独立准备的 COS Bucket 也应继续保留。

如果已经拆成 infra 和 apps，先在 apps 销毁应用，再到 infra 销毁集群和服务器。先删集群，Helm Provider 就可能无法访问 Kubernetes API，无法正常完成应用清理。

课件 README 中先用 state rm 移除 K3s 和 Argo CD 的记录，再销毁服务器。这会跳过相应对象的正常管理流程，不适合作为默认清理步骤。若发现销毁失败，先恢复必要的访问条件、检查依赖和远端对象，再决定如何处理状态。

最后到云控制台核对实验资源是否仍然存在，以及是否还残留需要付费的关联资源。state 为空只是一次状态检查，不能替代对云上环境的核对。
